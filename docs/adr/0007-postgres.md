# 7. Postgres 17 à la place de SQLite

Date : 2026-11-18 — Statut : accepté. Remplace le choix d'une base SQLite à une connexion (mono-utilisateur, D-3).

## Contexte

SQLite convenait à l'application locale. Hébergée (ADR 0006), derrière une authentification, appelée par d'autres applications,
elle partage la base avec plusieurs sessions simultanées ; les trois autres applications A-N-O-D-E-R sont sur Postgres 17.

## Décision

- Postgres 17, Flyway (`flyway-database-postgresql`), `JdbcClient` : la couche d'accès ne change pas.
- Les migrations V1 à V20 sont **réécrites en place** pour Postgres : aucune installation Postgres n'existait, et l'historique
  Flyway d'une base SQLite ne peut pas servir. Identifiants `bigint GENERATED BY DEFAULT AS IDENTITY`, dates `timestamptz`
  (les enregistrements portent des `OffsetDateTime`, sérialisés en ISO-8601 UTC), drapeaux `boolean`, `bytea` pour le hash des clés.
- `INSERT OR IGNORE` devient `INSERT … ON CONFLICT DO NOTHING`.
- Dev : `compose.yaml` + spring-boot-docker-compose. Tests : Testcontainers (`postgres:17-alpine`), une base par classe de test,
  des pools Hikari de 3 connexions et `max_connections=300` (un contexte Spring est gardé en cache par classe).
- Pas de migration des données SQLite : une installation existante repart d'une base vide.

## Conséquences

- Docker est nécessaire pour développer et tester.
- Postgres est typé : un test qui passait un id en `String` (SQLite le tolère) a dû passer un `long`, et un test qui lisait « le dernier
  id » de la mauvaise liste ne passait que parce que deux tables SQLite commençaient toutes deux à 1 (corrigé).
- Pas encore fait : OpenAPI, pnpm / React Query / vitest, Docker (image) et CI.
